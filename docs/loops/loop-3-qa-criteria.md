## 0. Preconditions: before any row counts

Loop 1's P1–P5 carry over unchanged: **isolation** (non-default ports, explicit `CONVEX_URL`,
explicit `HUB_URL`), **the isolation check proves it looked** (`p2-isolation.mjs`: empty before, the
probe present after), **`qa-` names**, **frozen tree** (clean at the start and the end; mutants and
seeds in `git archive` scratch copies), **receipts read with a parser**. Added for Loop 3:

- **P3 exception, H rows only.** H-AARON uses the literal name `aaron` on the throwaway stack, because
  the hub's startup registers that exact name as `human` (`src/index.ts:55`). P1 and P2 keep it off the
  main stack.
- **P6 No real key.** Every key in the run is generated by the harness (`key(n)`, a per-process
  salt) or by the candidate client inside the QA key directory. `A2A_KEY_DIR` points into `QA_TMP`
  for every client process. The real `~/.a2a-hub/keys` is listed **by file name only** before and
  after the run, and the two listings must be identical, or absent both times. No command in the run
  sets `AGENT_KEY` to a literal on its command line.
- **P7 Two modes, one database.** A warn hub and a strict hub (`AUTH_MODE=strict`) run the
  candidate against **the same** QA Convex. So a row is observed from both modes, not rebuilt for
  each. `GET /health` on each confirms which process is which, and a request with an unknown key is
  the known positive: strict answers 403 and warn answers 200.
- **P8 Seeded legacy state.** The pre-deploy state (shared short hashes, rows with no `keyStatus`)
  cannot be created by the candidate (U1 and the floor refuse it). It is seeded the way tcm's was:
  **the `ea9d057` hub against the `ea9d057` functions** on a fresh QA Convex. Then the candidate
  functions are pushed, as in the deploy act in miniature (design §4.2 step 3). Each seeded
  row is read back (name, 8-hex prefix, `keyStatus` absent) **before** the push, so the seed proves
  it landed.
- **P9 Log capture.** The stdout and stderr of every hub, daemon, proxy and client process go to
  separate files under `QA_TMP`. K6 scans them, and the log-line assertions below read them.

- **P10 Stop and prove, around every SIA full stop** (the SIA planner's condition for the hold's
  lift). During an SIA full suite or SIA B's Step 0 load measurement, the throwaway stack is
  **stopped, not idle**. Scratch Convex, including `convex-local-backend.exe`, and every hub, daemon
  and proxy process are killed **by PID**. Each PID is recorded at start, and its command line is
  checked for a QA port before it is killed. Then every QA port is shown free in both address
  families (`stop-stack.ps1`, below). The stack is not restarted until the SIA planner says the run
  has finished. A row interrupted by a stop is re-run from its setup, never resumed.

## Instruments

- **H — harness**, `qa/loop-3-harness-keys` @ `0ca2358` (Loop 1's harness, with per-seat
  throwaway keys, no default key, `talk()` never inherits `AGENT_KEY`, and `A2A_KEY_DIR` inside
  `QA_TMP`). Loop 3 rows are added as new scripts beside it. `whoami(k)` below means
  `GET /a2a/whoami` with `X-Agent-Key: k`, **parsed**: `{ name }`.
- **X — fault proxy** (Loop 1). Two additions, each validated on a known positive before its row
  counts: (a) a request log that records, per request, route, status, and **whether** an
  `X-Agent-Key` header was present and whether it equals the literal `dev-key`, never its value;
  (b) a rule `forward-then-drop` for `POST /a2a/rotate`: forward, let the hub commit, then destroy
  the client socket.
- **S — keyscan**, `docs/loops/loop-3-qa/keyscan.mjs`. **Validated at `ea9d057`:** over `src/
  scripts/ client/` it finds exactly the 7 `dev-key` code sites of Amendment 1 (4 of them
  `|| "…"` fallbacks), tags the 4 comment mentions separately, and exits 2 when told to expect 0.
- **A — K7 analyzer**, the Loop 2 approach: it streams `convex data agents --format jsonl` and prints
  counts and 8-hex prefixes only. It is extended with `keyStatus` and **re-validated on a synthetic
  known positive** before it counts. The positive has one row of each class: stale hash, shared hash,
  `legacy` row, row with no status, a `dev-key` holder, a non-JSON line, and an `AUTH_MODE` other
  than `warn`. Each must be flagged. It fails closed on zero rows parsed and on a count at the limit.
  *Built:* `loop-3-qa/k7-analyzer.mjs`. *Validated* 2026-09-24 by `k7-analyzer.selftest.mjs`, 13/13
  (each class flagged, a clean table passes, both fail-closed cases, the deploy phase). No output
  carried a full hash or an `agentCard`.
- **K — key-leak scanner** (K6). It runs **inside the harness process** that generated the keys. It
  reads every artifact and counts hits per artifact for every key used and every full sha256 of
  one. It prints counts, never values. **Known positive:** one key planted in a scratch file must
  be counted before the real scan counts.
  *Built:* `loop-3-qa/leakscan.mjs`. *Validated* 2026-09-24 by `--selftest`, 8/8 (planted key and
  hash counted, an 8-hex prefix and a foreign key not counted, key-shaped runs seen).
- **T — `stop-stack.ps1`** (P10): it kills recorded PIDs and any listener on a QA port whose command
  line names that port, then proves every QA port free. It exits non-zero while any port is taken.
  **Validated at the lift, before the first start,** against a known positive: a dummy listener on a
  QA port must be found, killed and shown gone.
- **M — mutants** as in Loop 1: shown landed, `tsc --noEmit` clean, observed to fire before judged.

**Both directions** means the state is asserted before the act and its opposite after, or a
positive and a negative case side by side. A check that could not tell a working rule from a
missing one passes nothing.

## Rows

### K1 — a key belongs to one name (U1, the floor)

Setup: candidate functions, both hubs. `qa-k1a` and `qa-k1b` register with distinct keys `ka` and
`kb`.

1. `whoami(ka) = qa-k1a` and `whoami(kb) = qa-k1b`, from both hubs. Neither key resolves to the
   other name.
2. **A new name presenting a held key.** `qa-k1c` registers with `ka`: **409 in warn and in
   strict.** The body contains neither `qa-k1a` nor any 8+ hex run from `ka`'s hash. Afterwards
   `agents:getByName(qa-k1c)` and `peers:getByName(qa-k1c)` are both null, and `whoami(ka)` is still
   `qa-k1a`.
3. **An owned name presenting another's key.** `qa-k1b` registers with `ka`: 409 in both modes, and
   `whoami(kb) = qa-k1b` afterwards.
4. **A legacy name moving onto a held hash.** A seeded legacy row (P8) registers with `ka`: 409 in
   both modes, and its stored prefix is unchanged.
5. **Floor, both sides of the boundary, both modes:** a new name with a 31-character key gets 400
   `key too short`, and no row is created. A new name with a 32-character key is 200, `owned`, and
   resolves.

**Fails if:** any register creates a second holder of a hash, any refusal changes a stored hash or
creates a row or peer, a response leaks the other name or a hash, or the floor's boundary is off by
one.

### K2 — rotation under strict (§2)

Setup: owned `qa-k2a` with key `k0`. Rotation is `POST /a2a/rotate` with `X-Agent-Key: k0` and body
`{ newApiKey: k1 }`, run directly and through `hub-talk --rotate-key`.

1. **Before:** `whoami(k0) = qa-k2a`, `whoami(k1)` has no name. **Rotate on the strict hub:** 200
   `{ ok, name }`, and the body contains neither key nor any hash run. **After, both directions:**
   `whoami(k1) = qa-k2a`. `k0` gets 403 on strict, and on warn it gets 200 with `name: null` plus
   one `WOULD REJECT unknown X-Agent-Key` line. A data read shows no row holding `k0`'s hash
   (V-003).
2. **Negative cases, both modes, each followed by `whoami(k1) = qa-k2a` (nothing rotated):**
   - wrong current key in the header: 403 `rotation requires your current key`;
   - no header: 401;
   - a legacy key in the header (a P8 row): 403;
   - `newApiKey` held by another name: 409;
   - `newApiKey` shorter than 32 characters, or equal to the current key: 400;
   - a body naming another agent (`{ name: "qa-k1a", newApiKey }`): only the caller is rotated, or
     the request is refused. `whoami(ka)` is still `qa-k1a`.
3. **Two rotations race with the same current key** (fired together): exactly one returns 200. The
   final key is that winner's `newApiKey`, and the loser's `newApiKey` resolves to no name.
4. **A second live instance, strict.** A candidate daemon `qa-k2d` runs with `k0` and is shown
   heartbeating first (known positive: `lastHeartbeatAt` advances). Rotate from a separate process.
   Its next hub call gets 403. It **exits 1** within two poll or heartbeat intervals, with
   `key rejected for qa-k2d` on stderr and no key there. It does not retry.
5. **A second live instance, warn** (ruling 1's note). The same on the warn hub. Its heartbeat gets
   `409 superseded`, and it **exits 0** by the heartbeat path as today. Between the rotation and its
   exit, its requests are unattributed (`WOULD REJECT unknown`). Steps 4 and 5 are both required;
   either alone fails K2.
6. **The old instance cannot restore its key.** Register `qa-k2d` with `k0`: 409 in both modes
   (C7), stored hash unchanged. Rotate back with `k0` in the header: 403.
7. **A new daemon takes over.** A daemon started with `k1` after the rotation registers and
   heartbeats with 200 within 60 s. The rotation's discarded lease has gone stale by then (§2.3).
8. **Interrupted `--rotate-key`** (X `forward-then-drop`). The hub commits, hub-talk sees a socket
   error, `<name>.key.next` exists, and `whoami(.next) = name`. The next hub-talk command promotes
   it, with a stderr note. Afterwards `.key` resolves to the name and no `.next` is left. No key
   appears on stdout or stderr at any point.

**Fails if:** the old key resolves after rotation in either mode, any negative case rotates, the
race has zero or two winners, either daemon path (403 exit 1 strict, 409 exit 0 warn) is missing,
the old instance restores its key, or an interrupted rotation loses the key silently.

### K3 — M3 killed with per-seat keys, standard setup only

1. `m3check.mjs` (harness @ `0ca2358`) against the candidate and an M3 mutant built from it
   (`GET .../messages` marks `req.agentName` through the last turn). **`M3.fires`** and
   **`M3.control`** pass. **`M3.devkey`** passes: `agents:getByKeyHash(sha256("dev-key"))` is null,
   the status is 403 or 200, and B is unmarked.
2. `rows.mjs A3` on the unmutated candidate passes, and on the mutant hub fails.
3. **"No special setup":** every key the run uses comes from `register`, `AGENT_KEY`, or a key file
   written by `--init-key`, the three paths the design documents. The report lists which path each
   row used.

**Fails if:** M3 survives, the control fails, or any seat's identity was produced by a path the
design does not document.

### K4 — `POST /read` checks `reader` against the caller (§5)

Setup: a room of `qa-k4a` and `qa-k4b`, with one turn from `qa-k4a` unread by `qa-k4b`.

1. **Strict, mismatch:** `reader: qa-k4b` with `qa-k4a`'s key gives **403** `reader is not the
   caller`, and `/reads` is unchanged (`qa-k4b.lastRead` still null).
2. **Strict, match:** `reader: qa-k4b` with `qa-k4b`'s key gives 200, and the mark moves.
3. **Warn, mismatch** (a fresh room): 200, the mark moves as today, and the log has
   `WOULD REJECT reader qa-k4b for caller qa-k4a on POST /read`.
4. **Warn, unknown key and legacy key:** 200, the mark moves, and the log says `caller unknown`.
5. **Receipts unchanged:** `rows.mjs A1 A2` pass on the candidate. hub-talk sends `reader = --as`
   with its own key, so it never mismatches.

**Fails if:** strict marks on a mismatch, strict refuses a match, warn refuses anything, or a log
line is missing or carries a key or hash.

### K5 — a client with no key does not become a shared identity (§3.2, §3.4; O4, O5)

1. **Static (S).** Over `src/ scripts/ client/` at the candidate: `dev-key` 0 and `fallback` 0 on
   code lines. Comment mentions are listed and not judged. The known positive is S's validation
   at `ea9d057` (7 and 4).
2. **Dynamic, each client with no `AGENT_KEY` and an empty key directory**, behind X:
   - `hub-talk --as qa-k5 --say x`: exit 1, stderr names `--init-key`, **zero requests in X's log**;
   - `daemon --name qa-k5d`: non-zero exit and zero requests;
   - `a2a-compliance-probe` with no `--key`, `AGENT_KEY` or `--as`: exit 1 and zero requests;
   - `ask-agent`, `demo-loop`, `verify-client-stack` (ephemeral keys): X logs no request carrying
     `dev-key`. Each one's registered name reads back `owned`, and its output contains no
     43-character base64url run and no 64-hex run.
3. **A different spelling of the hub fails loud.** The key file is under `127.0.0.1-<port>`, and
   `HUB_URL` spells the same hub `localhost:<port>`. The result is exit 1, stderr names the other
   directory, and no key contents appear.
4. **Old client, B side.** `hub-talk` from `ea9d057` with no `AGENT_KEY` defaults to `dev-key`. Its
   calls resolve to no name: `whoami(dev-key)` has no name while any legacy row holds it (U3).
5. **`client/`:** the key field starts empty. A built bundle contains no `dev-key` literal. The
   browser client is checked statically only (see "cannot see").

**Fails if:** any `dev-key` literal or literal fallback remains in code, any client with no key sends
a request, or any path makes `dev-key` resolve to a name.

### K6 — no key or full hash in files, commits, logs or transcripts

1. **K** scans every artifact of the run: every P9 log, X's log, harness outputs, the report, and
   `git diff <candidate-base>..<candidate>` plus the QA branch's own diff. The expected count is 0
   hits for every key and every full hash. **Throwaway keys are scanned too.** They are exempt
   from K6's definition (Amendment O6), but a hub that logs a throwaway key would log a real one.
   So they are the instrument that can see this.
2. **`--init-key` and `--rotate-key` output:** exactly name, hub, path and an 8-hex prefix. There
   is no 43-character base64url run and no 64-hex run on stdout or stderr, and the prefix matches
   the stored hash's.
3. **`classifyAtDeploy` output:** counts only, with no name printed next to a hash or prefix.
4. **Transcripts:** no command run by any seat in this loop sets `AGENT_KEY` to a literal, and no
   real key directory is read (P6). The report states this for the QA seat and asks Rivet to state it
   for the build.

**Fails if:** K counts any hit, or any output carries more than an 8-hex prefix.

### K7 — live, read-only, on Aaron's word for each act (D-007; design §4.2, §4.3 rev 3)

Run with A, read-only, after each act in design §4.2. **No request is sent to tcm with the
`dev-key`** (N1), and nothing is written. Under D-007 (master `e166057`), tcm's 8 `dev-key` rows
leave in two ways. **The unused four** (`clark`, `cursor`, `general`, `probe`) are released with
`agents:release` in the deploy act. **The live four** (`relay`, `atlas`, `forge`, `grok`) each get
their row replaced by their own `--init-key` (MIG: the legacy row is deleted and a fresh owned row is
inserted in one transaction).

0. **Pre-deploy (step 2):** 10 rows, none with a status. **`askPolicy` is counted by name**, and
   each policy found is recorded by fingerprint (A prints `askPolicy on N row(s): …` and an 8-hex
   fingerprint per name). This is the baseline for 3.
1. **After the deploy act** (push, `classifyAtDeploy`, the four releases, the hub): 6 rows,
   `keyStatus` 2 `owned` (`cursor-grok`, `grok-probe`) and 4 `legacy`, with the same prefixes as in
   0 for those 6. The four released names are absent. `AUTH_MODE` is `warn`. (`--phase deploy
   --expect-rows 6 --expect-owned 2 --expect-legacy 4 --expect-absent clark,cursor,general,probe`.)
2. **After each live name's `--init-key`:** that name has exactly one row, it is `owned`, its `_id`
   tail differs from its tail in 0 (the row was replaced), and its prefix matches the printed one. No
   other row changed.
3. **`askPolicy` restored:** every name that carried a policy in 0 carries the same policy again
   after its re-registration (`--expect-askpolicy name=<fingerprint from 0>`). A fresh row drops it,
   so this fails until the policy is set again.
4. **At completion (step 10), the end state:** `cursor-grok` and `grok-probe` are `owned` with their
   prefixes from 0. **Every re-registered name is `owned`**, and its prefix matches its
   `--init-key` print. **No row holds the `dev-key` hash (prefix `7e9f8fd1`)**, there are **no
   `legacy` rows** and no rows without a status, every hash has exactly one holder, no stale hash
   resolves, and `AUTH_MODE` is `warn`. The name set is exactly `cursor-grok`, `grok-probe` and the
   re-registered names (`--expect-names`). Any released name not re-registered is absent.
5. **Second signal:** after step 9, the hub log has no `WOULD REJECT legacy` line for a working
   day. This is a read-only count of lines, on Aaron's word.

A (`k7-analyzer.mjs`) is re-validated after its `askPolicy` and `_id` additions: selftest 21/21,
including a policy dropped by a fresh row (fails) and a policy set again (passes).

**Fails if:** any condition in 1–4 is false, an act changed a row other than its own, A was not
re-validated, or a read wrote anything.

### MIG — migration replaces the row, atomically (design §4.1 rev 3)

Setup (P8): the legacy row `qa-mig` shares a short key with `qa-mig2`, through the `ea9d057`
functions. It carries an `askPolicy` (seeded with the `ea9d057` `agents:register` mutation, which
accepts one) and it is in a room with turns and a receipt mark. Record its `_id` and take REL's
snapshot.

1. **Poller, known positive first.** A tight loop of `agents:getByName("qa-mig")`, run
   concurrently, must **see `null` at least once** across a two-act replacement (`agents:release`,
   then a separate `--init-key`) on a control name. Only then can its silence below count.
2. **`qa-mig --init-key`** (warn) with the poller running: **the poller never sees `null`** and never
   sees two rows. Afterwards there is **exactly one row for `qa-mig`**, `owned`, with a **new
   `_id`**. The old `_id` is gone (`convex data agents` has no row with it). The log has `MIGRATE
   qa-mig: legacy row replaced by a fresh owned row`.
3. **The fresh row keeps nothing:** there is no `askPolicy` (it was present before), and the lease is
   the new instance's (`activeInstanceId` set, `lastHeartbeatAt` ≥ the act).
4. **Everything else is untouched:** REL's snapshot of `peers`, `sessions`, `sessionPeers` and
   `messages` for `qa-mig` is deep-equal before and after. `qa-mig2` reads `legacy` (stamped, not
   promoted), and the shared key resolves to no name.
5. **The room still works:** `qa-mig --session <room> --inbox` exits 0, and the mark moves.

**Fails if:** a zero-row or two-row moment is observed, the old `_id` survives, more than one row
exists, the fresh row inherits a policy, or anything outside the name's `agents` row changes.

### REL — `agents:release` removes only the agents row (D-007; design §4.3 rev 3)

On tcm this is the path of the unused four, and it is the operator's repair. The live names use MIG.

Setup (P8): `qa-rel` and `qa-rel2` share a short key `s` through the `ea9d057` hub, with no status.
`qa-rel` is in a room with `qa-relx`. It has sent turns there, and it has a receipt mark. **Known
positive first:** the snapshot instrument sees non-zero counts for every table below.

1. **Snapshot before** (public queries and `convex data`, parsed): the `agents` rows for `qa-rel`
   (1), its `peers` row (whole row), and every `sessions`, `sessionPeers` and `messages` row that
   involves `qa-rel`, whole rows, with counts.
2. **`agents:release({ name: "qa-rel" })`** with the scratch admin key (`convex run`).
3. **Snapshot after, both directions:** the `agents` rows for `qa-rel` go from 1 to **0**. The
   `peers` row and every `sessions`, `sessionPeers` and `messages` row are **deep-equal** to
   before, with the same counts. No other name's `agents` row changed.
4. **Stamping:** `qa-rel2`, now the only holder of `s`, reads `legacy`, not `owned`. It was not
   promoted by the release. `whoami(s)` has no name on both hubs.
5. **Release is admin-only:** the same call through the public Convex API (`/api/mutation`) is
   refused, and a snapshot shows nothing changed. Releasing a name with no row changes no row.
6. **Fresh re-registration:** `qa-rel --init-key` from the candidate client exits 0. Its row is
   **inserted `owned`**, and its prefix matches the printed one. `whoami(key) = qa-rel`. The `peers`
   row is still the same row (same `_id`, same `type`), and the room's history is readable and
   receipts work: `qa-rel --session <room> --inbox` exits 0 and the mark moves.
7. **Report only (Relay's ruling), not judged:** what the `ea9d057` client (`dev-key`) sees on the
   released name before any `--init-key`. The design (§4.3 rev 3) says: its register is refused; it
   **talks unattributed** (its `peers` row survives, so `sessions.create` and `messages.send`
   succeed); it is missing from `/a2a/agents/live`; and its heartbeats are no-ops. The report
   records each against that statement. **Prevention is by rule, and the rule is checked in B1.2.**

**Fails if:** release removes or alters anything but the name's `agents` row, promotes another
holder, can be called publicly, or the fresh `--init-key` does not insert an owned row that works
in the old room.

### H-AARON — the browser client as the human peer `aaron` (design §12, rev 3)

Name `aaron`, **pending Aaron's confirmation**. If he picks another name (for example `aaron-web`),
only H2's name changes. The stack is the throwaway one (P3 exception). `hub-key.mjs` runs with
`HUB_URL` at the QA hub and `A2A_KEY_DIR` in scratch.

- **H1. Registration never changes an existing peer's type** (`peers.ensure`).
  1. The hub's startup registers `aaron` as `human` (read `peers`: `type: "human"`). This is the
     known positive that the instrument reads the type.
  2. `hub-key.mjs init --as aaron --kind human`: `peers.aaron.type` is still `human`. It is still
     `human` after a **hub restart**, and after a **second register** with `aaron`'s own key.
  3. **An agent registering the name of an existing human peer that has no agents row** (a
     `qa-human` peer made with `peers.register(type: "human")`, then `/a2a/register` as `qa-human`
     with `kind: "ide-session"`): the type stays `human`, and `metadata` is unchanged. **Both
     directions:** a brand-new name registered with `kind: "ide-session"` gets `type: "agent"`, and
     one registered with `kind: "human"` gets `type: "human"`.
  4. **An agent cannot re-register `aaron`:** a register of `aaron` with any other key gets 409 (C7),
     and the type and stored hash are unchanged.
- **H2. `aaron` has an owned agents row of kind human:** exactly one row, `keyStatus: "owned"`,
  `agentCard.kind: "human"`. `whoami(aaron's key) = aaron`. U1, the floor and rotate apply: a
  rotate on it passes K2.1 as for any row.
- **H3. Human rows are never online agents.**
  1. `agents:listOnline` and `GET /a2a/agents/live` leave out `aaron`. **Known positive:** a
     `qa-` agent registered at the same moment is listed.
  2. **Escalation never picks `aaron`:** `escalateToAgent(msg)` with no named target (the
     candidate's `src/escalation.ts`, against QA Convex):
     - with `aaron` as the only row, it returns the "No agents are currently online" text and creates
       no task;
     - with `aaron` and one `qa-` daemon row, the task's `assignedAgent` is the daemon (known
       positive; the call is stopped once the task row exists).
  3. The old hub on candidate functions (B2) does not list `aaron` either.
- **H4. The browser holds the key without it being printed.**
  1. Static, `client/src/App.svelte`: the Key field's initial value is empty, the input is
     `type="password"`, and every `localStorage` access is inside `try`/`catch`. There is no key
     literal (K5's S scan).
  2. `hub-key.mjs copy --as aaron`: its stdout and stderr are exactly `copied key for
     aaron@<hub-id> (prefix xxxxxxxx)`. K finds 0 key or hash hits and 0 key-shaped runs in them.
     The prefix matches the stored hash's. The clipboard, read inside the harness process and never
     printed, equals the key file. The run's last step overwrites the clipboard, because the
     throwaway key must not stay on Aaron's clipboard.
  3. With no key, the browser's requests get 401 (the route behaviour, checked with the harness's
     keyless `hub()`).

**Fails if:** any path changes `aaron`'s peer type, `aaron` is listed as online or picked by
escalation, `copy` prints more than the prefix line, or the Key field starts filled.

### K8 — a migrated name keeps its key (C7, O1)

Setup: a P8 legacy row `qa-k8` holding a shared short key `s`, with other legacy holders of `s`.
**Known positive first:** `qa-k8` migrates to `m` (warn, `MIGRATE` logged; the row is replaced, as MIG checks). This shows the register
path can change a stored hash, so the no-change results below are not those of an inert instrument.

Then in warn **and** in strict, for each presented key, the stored prefix of `qa-k8` stays `m`'s,
and `whoami(m) = qa-k8` after every attempt:

- `s` (its old key): 409 while other names hold `s` (U1), or 400 once none do (floor);
- a fresh 43-character key: **409 `name holds its own key; use rotate`**, and `whoami(fresh)` has no
  name;
- `m` itself: 200 (as a heartbeat), stored hash unchanged.

And with `hub-talk` from `ea9d057` on `qa-k8` with `dev-key`: its register is refused (log), its
say, wait and inbox still work in warn with exit codes as against the old hub, and `whoami(m)` is
still `qa-k8` after it.

**Fails if:** any register on an owned name changes its stored hash, in either mode.

### R1 — ownership is stored, not derived from a count (ruling 1; design §1.1, §4.4)

Setup (P8): `qa-r1a`, `qa-r1b` and `qa-r1c` registered through the `ea9d057` hub with **one short
key `s`**. Also `qa-r1u` with its own 43-character key, as the control. Then push the candidate
functions (**not** `classifyAtDeploy` yet) and start the candidate hubs. At every step, check `s`
from both hubs: **`whoami(s)` has no name on warn, and gets 403 on strict.**

0. **Before:** 3 rows share `s`'s prefix, none has a `keyStatus`, and `s` resolves to no name.
1. `qa-r1a --init-key` (candidate hub-talk, QA key directory): exit 0, and `whoami(ka) = qa-r1a`.
   Its row is replaced (new `_id`, exactly one row, `owned`).
   `s` resolves to no name.
2. `qa-r1b --init-key`: exit 0, and `whoami(kb) = qa-r1b`. **`qa-r1c` is now the only holder of
   `s`, and `s` still resolves to no name.** It was not promoted by attrition. Data: `qa-r1c` reads
   `legacy`.
3. **`classifyAtDeploy` now** (Rivet's fourth step): its output is counts only. `qa-r1c` **stays
   `legacy`** (the stamping layer), `s` still resolves to no name, and `qa-r1u` becomes `owned` and
   resolves (the control: classify does promote when it should). A second run changes nothing (the
   data diff is empty).
4. `qa-r1c --init-key`: **exit 0 (the last holder still migrates)**, and `whoami(kc) = qa-r1c`. No
   row holds `s`.

**Both directions** at steps 1–4: `ka`, `kb` and `kc` each resolve only to their own name.

**Fails if:** `s` resolves to any name at any step, the last holder cannot migrate, classification
promotes `qa-r1c`, or the control is not promoted.

### N — no flag day across the cutover (§3.6; brief "must be preserved")

### B1 — a new name on the old client, between deploy and step 9 (ruling 2; design §11)

Setup: the candidate warn hub. An existing room between two registered `qa-` seats. The client
under test is `ea9d057` hub-talk with no `AGENT_KEY` (so `dev-key`), behind X. It runs twice: while
P8 legacy rows hold `dev-key` (register refused by U1, 409 in X's log), and after the last one has
migrated (refused by the floor, 400).

1. **The refusal is loud, with the right cause.** `--as qa-b1-<tag> --session <room> --say x`: exit
   1, and stderr contains `not registered on this hub`. It must not show a bare `Unknown peer`.
   Afterwards, `agents:getByName` and `peers:getByName` for the name are both null, and the room
   has no turn from it.
2. **The other paths of §11's table**, each observed and matched to the design's column:
   - `--peer <a registered seat> --say x`: exit 1, `not registered on this hub`, no session created;
   - `--session <room> --wait` and `--inbox`: they read the room, the receipt failure is on stderr,
     and there is no mark for the name in `/reads`;
   - no-arg lobby mode with no peer opening it, `--join-timeout 5`: exit 1 `no live IDE peer`. This
     is the silent path, and the design closes it by rule, not code. So **the rule is checked in
     text:** "a new seat name, or a released one, is created (or re-created) only by `--init-key` from the new-client worktree" (revision 3 extends it to released names) is in
     `joining-the-hub.md` and in the Q1 text sent to the SIA planner (the record's copy).
3. **The rule's remedy works.** `--init-key` for the same name from the candidate client (QA key
   directory), then the same old-client `--say`: exit 0, a turn from the name, and the name's stored
   prefix is unchanged by the old client's refused `dev-key` register (C7).

**Fails if:** any old-client path exits 0 without the name being registered, any refused register
leaves an `agents` or `peers` row, the cause is not named, the rule text is missing, or the remedy
fails.

### B2 — the old hub against the new functions (ruling 2; design §11)

Modelled on Loop 1's `skew.mjs`. Hubs: the `ea9d057` app on `ea9d057` functions (baseline), the
**`ea9d057` app on candidate functions** in warn and in strict, and the candidate app on
`ea9d057` functions (step 5 only). Keys: **legacy** (a P8 row), **shared** (a P8 hash with two
holders), **unknown** (43 characters, never registered) and **owned** (registered through the
candidate).

1. **Function level.** `agents:getByKeyHash` returns exactly `null`, not an object, for the legacy,
   shared and unknown hashes. For the owned hash it returns an object whose `name` is the owner. That
   is the known positive, and it shows the nulls are not inert. `agents:keyHashStatus` returns
   exactly one of the strings `owned`, `legacy`, `shared` and `unknown`, each matching its key,
   and nothing else (no name, no hash).
2. **Old app on candidate functions, on a guarded GET:** strict gives 403 for legacy, shared and
   unknown, and 200 for owned. Warn gives 200 for all four, with the old hub's `WOULD REJECT
   unknown` line for the first three and no line for owned.
3. **A refused register through the old app** (U1: a new name with the owned key; C7: the owned name
   with a fresh key). Each is non-200, makes no `peers` row, and leaves every stored prefix
   unchanged.
4. **No return shape changes outside §11's table.** A static diff of every exported function in
   `convex/` between `ea9d057` and the candidate, against every `api.*` call in `ea9d057`'s `src/`.
   Every function the old hub calls has an unchanged argument validator (new arguments optional
   only) and return shape, or appears in §11's table with the change stated there. The search is
   validated on a known positive: it must list `agents.getByKeyHash` and `agents.register` as
   called by the old hub.
5. **The auth decision never depends on `keyHashStatus`.** On the candidate app against `ea9d057`
   functions (the query does not exist there), an unknown key gets strict 403 or warn 200, never
   500. The log line says `unknown`.
6. **Old client scenario** (as N.1) with the owned key: the old app on candidate functions gives the
   same exit codes and stdout as on `ea9d057` functions.

**Fails if:** any non-authenticating result reaches the old hub as anything but `null`, strict on
the old app admits a legacy, shared or unknown key, a refused register leaves a peer row or changes
a hash, a changed return shape is missing from §11's table, or a `keyHashStatus` failure changes
an auth decision.

## What these criteria cannot see

- **A hostile process under the same OS user** can read every key file (design §3.2 threat model).
  Out of scope.
- **Direct Convex callers on the tailnet** (T-057). The rules in the mutations hold for them. Other
  public functions are not tested here.
- **Other caller-asserted identities**: heartbeat `:agentId`, message `from`, task claim (T-058).
- **The browser client's behaviour.** It is checked statically only.
- **tcm's live behaviour** beyond K7's data read and log count. No request is sent to tcm.
- **Races beyond two concurrent rotations.** Convex serialisation is trusted, not proven.
